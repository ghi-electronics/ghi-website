---
title: "Graphics"
---

Graphics on Endpoint are deliberately not tied to any particular drawing
library. The `DisplayController` accepts a raw pixel buffer and flushes it
to the panel — the application is free to produce that buffer with
whichever graphics library it prefers, as long as the pixel format matches
the display configuration.

The common pattern is the same in every language:

1. Allocate a buffer the size of the display (for example, *width* × *height* × 2
   bytes for 16-bit RGB565).
2. Draw into the buffer using any 2D graphics library.
3. Pass the buffer to `DisplayController.Flush`.

Partial-region updates are supported for applications that redraw only
what changed, reducing bandwidth and CPU use.

## .NET

The .NET runtime on Endpoint is standard .NET, so any NuGet-published 2D
graphics library that renders to an in-memory bitmap is usable. Common
choices include:

- **SkiaSharp** — a full-featured 2D canvas with text, paths, gradients
  and image decoding, published by the SkiaSharp project. Requires the
  matching `SkiaSharp.NativeAssets.Linux` package for the ARM runtime.
- **ImageSharp** — pure-managed image processing (resize, filter,
  encode), useful when the hardware JPEG decoder is not involved.
- **System.Drawing.Common** — the classic GDI+-style API for simple
  shapes and text.

Any of these produce a byte array (or raw pixel memory) that can be
copied — optionally with a format conversion to RGB565 — and handed to
`DisplayController.Flush`.

## Python

Python applications use the standard Python imaging ecosystem — most
commonly **Pillow** (`pip install Pillow`), which provides an `Image` and
`ImageDraw` API similar in shape to .NET's graphics libraries. Pillow
ships prebuilt wheels for 64-bit ARM, so no cross-compilation is
required. Produce an image in-memory, extract the raw byte buffer with
`Image.tobytes()`, and flush it to the display.

For scientific or data-visualisation workloads, `numpy` and `matplotlib`
work the same way they do on a desktop; render into an off-screen canvas
and flush the resulting pixel buffer.

## C/C++

The C/C++ runtime ships with **LVGL** embedded in `libendpoint`. LVGL
provides a full canvas drawing surface (`lv_canvas`) and all the primitives
needed for 2D graphics — lines, rectangles, text, images — rendered into a
buffer in whichever pixel format is configured. Applications typically
reuse the same LVGL canvas that the UI widgets draw into.

Teams that prefer another library can link any standard C/C++ 2D graphics
toolkit (Cairo, STB image, custom code) and feed the resulting pixel
buffer to the display the same way.

## Pixel format

The display's expected pixel format is set in the parallel display
configuration (16-bit RGB565 is the common default). The graphics library
can either draw natively in that format or draw in a wider format (RGB888,
ARGB32) and convert to the panel's format on the way to `Flush`. See
[Displays](displays.mdx) for the configuration and flush API.
